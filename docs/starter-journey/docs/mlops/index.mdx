# 14. MLOps

> **You'll understand** how Databricks connects feature engineering, model training, deployment, and inference into a governed production lifecycle.
>
> **Prereqs:** [7. Build the first pipeline](/docs/build-first-pipeline/), [Unity Catalog foundations](/docs/before-you-start/foundations/unity-catalog), [13. CI/CD and DevOps](/docs/ci-cd-devops/)

## Why this matters

You know you need MLOps when you hit one of these three situations:

- **The model broke and nobody knows why.** It worked last quarter. Now it's degrading. The training notebook was overwritten, the hyperparameters were never saved, and the data it trained on has since changed. There is no way to reproduce the previous version.
- **Two teams, two answers.** Two pipelines compute the same input feature — say, `customer_30d_spend` — with slightly different logic. The models trained on each definition disagree, and both teams think theirs is correct.
- **Deploying a model update is a manual ritual.** Updating a serving endpoint means editing configs by hand across dev, staging, and prod, running undocumented CLI commands, and hoping nothing breaks. If it does break, there is no rollback.

The subpages that follow address these failure modes.

## Mental model

The MLOps lifecycle on Databricks flows in one direction: features feed training, training produces a registered model, the model gets served, inference generates predictions, and observability data feeds retraining. [MLflow](https://docs.databricks.com/aws/en/mlflow/) is the tracking layer throughout. Unity Catalog governs every artifact — feature tables, model versions, and inference outputs — with the same permissions and lineage you already applied to data pipelines.

![Databricks-managed MLflow manages the ML model lifecycle — Feature Store feeds Model training, Tracking logs every run, Model Registry centralizes versioned artifacts, Model Serving exposes the endpoint, and Monitoring captures requests and responses.
