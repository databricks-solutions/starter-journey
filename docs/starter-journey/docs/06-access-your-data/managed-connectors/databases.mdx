# Databases

> **You'll deploy** a Lakeflow Connect CDC pipeline for a database source, gateway plus serverless ingestion, defined with DABs, in ~15 min.
>
> **Prereqs:** [Lakeflow Connect ingestion overview](/docs/06-access-your-data/managed-connectors), a Unity Catalog connection to the source database, and the Databricks CLI installed and configured

## What you'll build

A database CDC pipeline has two halves, and the split is the whole reason databases differ from SaaS sources:

- The **ingestion gateway** runs on classic compute inside your own network, so it can reach the database and read its change feed. It stages change events into a UC Volume.
- The **serverless ingestion pipeline** reads the staged events and applies them to Delta tables with CDC semantics.

You define both as code with Databricks Asset Bundles (DABs), so the pipeline is version-controlled and repeatable instead of clicked together in the UI.

## What changes for your source

The pattern is identical across databases. Only the source-side change mechanism differs. Set that up on the database first, then the DABs definition is the same shape for all of them.

| Source | Change mechanism to enable | Notes |
|---|---|---|
| SQL Server | Change Tracking (CT) or Change Data Capture (CDC) | CT is lighter and gives latest-state-per-key. Use CDC when you need per-event history. Enable with `ALTER DATABASE ... SET CHANGE_TRACKING = ON` or `sys.sp_cdc_enable_table`. |
| PostgreSQL | Logical replication slot + publication | Create a replication slot and a publication, then name them in the pipeline's `source_configurations`. |
| MySQL | Binary logging (binlog) | Enable row-based binlog on the source. |
| Oracle | Query-based (no gateway) | Oracle ingests through periodic queries, not a change feed. It skips the gateway. Higher source load, no per-event history. |

:::warning
Change Tracking and CDC are not the same thing. CT tells you which rows changed; CDC keeps the full change log. Pick CT unless a downstream job needs the history, since CDC adds overhead on the source.
:::

## Prerequisites

- A Unity Catalog connection to the source database.
- The Databricks CLI installed and configured.
- A user or service principal with permission to create pipelines, and workspace-admin access to deploy (the provider uses a workspace-level connection).
- The source database has its change mechanism enabled (see the table above), and the gateway compute can reach the database over the network (VPC peering, PrivateLink, or a private link for on-prem).

## Steps

<StepGuide
  description="Define the gateway and ingestion pipeline as DABs YAML with an explicit classic compute block, replace the placeholders, then deploy and start it from the CLI."
  minutes={15}
  referenceHref="https://docs.databricks.com/aws/en/ingestion/lakeflow-connect"
  referenceLabel="Lakeflow Connect (Databricks docs)">

<Step>

Define both pipelines in your DABs YAML. The gateway pipeline gets an explicit classic compute block, which is what lets it reach the source over the network. The ingestion pipeline references the gateway by ID and lists the tables to land.

The example below uses PostgreSQL. For SQL Server, MySQL, or Oracle, keep the same shape and swap `source_type` plus the `source_configurations` block for your source's change mechanism.

Add this to your DABs `resources` block:

```yaml
variables:
  gateway_name:
    default: postgresql_gateway_pipeline
  pipeline_name:
    default: postgresql_pipeline
  dest_catalog:
    default: development
  dest_schema:
    default: c360_source

resources:
  pipelines:
    gateway:
      name: ${var.gateway_name}
      gateway_definition:
        connection_name: <my-connection>
        gateway_storage_catalog: development
        gateway_storage_schema: ${var.dest_schema}
        gateway_storage_name: ${var.gateway_name}
      target: ${var.dest_schema}
      catalog: ${var.dest_catalog}

      clusters:
        - label: default
          # AWS instance types. For Azure use Standard_DS3_v2 / Standard_DS4_v2
          driver_node_type_id: r5.xlarge
          # AWS instance types. For Azure use Standard_E8ds_v4 / Standard_E16ds_v4
          node_type_id: m5.xlarge
          autoscale:
            min_workers: 2
            max_workers: 4
            mode: ENHANCED

    pipeline_postgresql:
      name: ${var.pipeline_name}
      ingestion_definition:
        ingestion_gateway_id: ${resources.pipelines.gateway.id}

        source_type: POSTGRESQL
        objects:
          - table:
              source_catalog: your_database
              source_schema: public
              source_table: orders
              destination_catalog: ${var.dest_catalog}
              destination_schema: ${var.dest_schema}
          - schema:
              source_catalog: your_database
              source_schema: public
              destination_catalog: ${var.dest_catalog}
              destination_schema: ${var.dest_schema}
        source_configurations:
          - catalog:
              source_catalog: your_database
              postgres:
                slot_config:
                  slot_name: db_slot
                  publication_name: db_pub
      target: ${var.dest_schema}
      catalog: ${var.dest_catalog}
```

:::danger
The provider must use a workspace-level connection, and the service principal deploying the pipeline needs workspace-admin access.
:::

</Step>

<Step>

Replace the placeholders:

- `<my-connection>` with the name of your UC connection.
- `your_database`, `public`, and `orders` with your actual source database, schema, and table names.
- `dest_catalog` and `dest_schema` to match your governance model.
- For Azure, swap the instance types to the Azure equivalents noted in the comments.

For SQL Server, MySQL, or Oracle, set `source_type` accordingly and replace the `postgres` `source_configurations` block with your source's change mechanism.

</Step>

<Step>

Deploy the pipeline.

```bash
databricks bundle deploy
```

</Step>

<Step>

Start the pipeline.

```bash
databricks bundle run pipeline_postgresql
```

</Step>

</StepGuide>

## Where people trip

<details>
<summary>Gateway pipeline fails to start</summary>

The gateway runs on classic compute in your network. Check the cluster config (instance types, autoscale settings) and confirm the workspace can launch clusters with those instance types. If the default instance type is not stocked in your region, pin a regionally available one with a cluster policy.
</details>

<details>
<summary>Ingestion pipeline cannot connect to the source</summary>

The gateway cluster needs network access to the source database. Check VPC peering, security-group rules, and firewall settings, and confirm the connection object still has valid credentials. On-prem sources need a private link (ExpressRoute on Azure, Direct Connect on AWS, Cloud Interconnect on GCP).
</details>

<details>
<summary>Permission error when creating the pipeline</summary>

Whoever runs `databricks bundle deploy`, user or service principal, needs workspace-admin access or explicit permission to create pipelines. Check the workspace admin settings.
</details>

<details>
<summary>Pipeline state diverges from the source after a month</summary>

The staging Volume between the gateway and the ingestion pipeline keeps 30 days of change events by default. To reprocess further back, resnapshot the affected tables, or raise the Volume retention if this recurs.
</details>
